# T8 — 커버 이미지 업로드

- 상태: **완료** · 브랜치: `feature-cover-images` · 의존: T3 · 커밋 계획: 2개 — 업로드·서빙 API / 위저드·표시 전환
- 슬롯: T3 이후 아무 때나(다른 티켓과 독립). **T7 배포 전 권장**, 밀리면 09-02에 하고 재배포
- 설계 근거: [server-design.md](../server-design.md) §2(스키마)·§4(API)

## 목표

만들기에서 이모지 대신 **실제 썸네일 이미지**를 올릴 수 있다. 업로드한 플롯은 홈 카드·프로필·
채팅 아바타·대화 목록에 이미지로 보이고, 안 올리면 기존 이모지+그라디언트가 그대로 폴백이다.

## 범위

- **포함**: images 저장·업로드/서빙 API, 위저드 업로드 UI(클라이언트 리사이즈), 표시 컴포넌트 전환
- **제외**: 기존 플롯의 이미지 교체(수정 화면 자체가 스코프 외), 이미지 검수/신고(README 한계 명시), 외부 오브젝트 스토리지 연동(인터페이스만 분리)

## 저장 방식 결정

**DB(bytea) 저장 + 스토리지 인터페이스 분리** — 데모 조건에서의 선택.

- 외부 서비스·env 키 없이 로컬 docker와 Neon에서 **동일하게 동작**(env 가이드 원칙과 일관 — 키 없는 로컬 실행 유지)
- 클라이언트 리사이즈 후 ~200KB 수준이라 데모 규모에서 Neon 무료 티어(512MB)로 충분
- 코드에서 저장 접근을 `save/get` 인터페이스로 분리해, 실서비스라면 오브젝트 스토리지+CDN으로
  교체되는 지점임을 구조로 보여준다(README 한계에도 명시)
- 대안이었던 Vercel Blob은 더 실서비스답지만 로컬에 토큰(env)이 필요해지고 외부 종속이 늘어남 — 기각

## 작업 항목

### 업로드·서빙 API (커밋 1)

- [x] 스키마 추가(T1의 스키마에 편입) — `images`: id uuid PK · owner_id FK · content_type · bytes bytea · width · height · created_at / `plots.cover_image_id` FK 널 허용
- [x] `POST /api/uploads` — 로그인 필수, multipart. 서버 검증: **매직 바이트**로 jpeg/png/webp 확인(확장자·Content-Type 헤더 불신), 2MB 상한(413), 픽셀 크기 상한. 응답 `{id}`
- [x] `GET /api/images/[id]` — bytea 응답, `Cache-Control: public, max-age=31536000, immutable` + ETag, 없는 id 404
- [x] `POST /api/plots`가 `coverImageId` 수용 — 본인이 올린 이미지만 연결 가능(타인 이미지 id 거부)
- [x] 저장 접근 `save/get` 인터페이스 분리(구현체는 DB)

### 위저드·표시 전환 (커밋 2)

- [x] 위저드 1단계에 **커버 이미지 필드(선택)** — 파일 선택 → canvas로 4:3 크롭·최대 800×600 리사이즈·webp 재인코딩(EXIF 제거 겸, ~0.8 품질) → 미리보기 → 제출 시 업로드 후 plot에 연결. 이모지·그라디언트 선택 UI는 폴백 설정으로 유지
- [x] `PlotCover` 일원화 — cover_image_id 있으면 `<img>`(alt=플롯 이름), 없으면 이모지+그라디언트. 홈 카드·프로필 헤더·채팅 아바타·대화 목록·위저드 미리보기 전부 이 컴포넌트 경유
- [x] 시드 플롯 12개는 변경 없음(이모지 유지 — 폴백 경로의 상시 검증 겸)

## 테스트

- [x] 통합(docker DB) — 업로드: 정상 webp 저장·2MB 초과 413·**가짜 확장자(매직 바이트 불일치) 400**·비로그인 401 / 서빙: content-type·캐시 헤더·없는 id 404 / 플롯 연결: 본인 이미지 성공·타인 이미지 id 400
- [x] E2E 시나리오 추가 — 위저드에서 이미지 첨부 → 홈 카드·프로필에 썸네일 표시 → 미첨부 플롯은 이모지 폴백 유지

## 구현 노트

- 클라이언트 재인코딩이 1차 방어(용량 축소 + EXIF 등 메타데이터 제거), 서버 매직 바이트 검증이 2차.
  업로드 원본은 서버에 도달하지 않는다(재인코딩 결과만 전송).
- `<img>`에는 width/height 지정으로 레이아웃 시프트 방지, `loading="lazy"`(홈 그리드).
- 이미지 응답은 immutable 캐시라 교체 개념이 없다 — 교체가 생기면 새 id 발급(현재는 수정 없음이라 무관).
- 실서비스 전환점(README 한계에 명시): 오브젝트 스토리지+CDN, 업로드 검수/신고, 이미지 교체.

## 완료 기준

- 이미지 올린 플롯이 홈·프로필·채팅 아바타·대화 목록에 썸네일로 표시, 미첨부는 이모지 폴백
- 큰 파일(2MB+)·비이미지 파일 거부가 사용자 에러 메시지로 안내됨
- "테스트" 섹션 전부 통과(`pnpm test` + `pnpm e2e`)

## 검증 방법

- `pnpm test` + `pnpm e2e` — 완료 기준에 포함
- 수동: 10MB급 원본 사진 첨부(리사이즈로 통과 확인), 확장자만 바꾼 텍스트 파일 거부 확인
- `pnpm typecheck && pnpm build`

## 구현 결과 (2026-09-01)

커밋 2개(업로드·서빙 API / 위저드·표시 전환). `pnpm test` 126개(T8에서 29개 추가) +
`pnpm e2e` 5개(T8에서 2개 추가) 통과, `pnpm typecheck`·`pnpm build` 통과.
수동 확인: 3000×2000 · 7MB JPEG를 위저드에 첨부 → 브라우저에서 800×600 · 237KB webp로
줄여 업로드 성공(홈 카드·프로필·채팅 아바타·대화 목록 전부 썸네일), 확장자만 `.png`인
텍스트 파일은 "이미지를 읽지 못했어요…"로 거부, 시드 플롯 12개는 이모지 폴백 유지.

- **화면에는 이미지 id가 아니라 URL을 내려보낸다** — `PlotView.coverUrl`. 표시 컴포넌트가
  URL 조립 규칙을 알 필요가 없고, 무엇보다 **위저드 미리보기가 아직 서버에 없는 blob URL을
  같은 자리에 끼워 넣을 수 있다**. 서버 매핑과 클라이언트가 `coverImageUrl()` 한 곳을 공유한다.
- **픽셀 크기도 서버가 직접 읽는다.** 매직 바이트만 보면 "진짜 이미지인 20000×20000"이 통과한다.
  jpeg는 SOF 세그먼트를, png는 IHDR을, webp는 VP8/VP8L/VP8X 세 갈래를 각각 파싱해
  2000px 상한을 건다. 이 파서는 실제 인코더가 만든 파일 5종으로 유닛 테스트한다.
- **타인 이미지 id와 없는 이미지 id의 응답을 같게 맞췄다** — T3의 "비공개 플롯 = 미존재"와 같은 이유로,
  메시지가 다르면 남의 이미지 id가 존재하는지가 새어 나간다.
- **업로드 상한은 두 번 건다** — `content-length`로 본문을 읽기 전에 한 번(대용량 요청이 메모리에
  올라오지 않게), 파싱 후 실제 바이트로 한 번. 둘 다 413이다.
- **재인코딩 품질을 3단계로 낮춰 재시도한다**(0.8 → 0.6 → 0.4). 800×600 webp가 2MB를 넘는 일은
  사실상 없지만, webp를 못 만들어 png로 떨어지는 브라우저에서는 가능해서 남겨 뒀다.
- **`PlotAvatar` 내부만 고쳐 채팅 아바타·대화 목록·내 플롯 목록이 한꺼번에 전환됐다** — 같은 시각
  진행 중인 T4(채팅 영속화)와 파일이 겹치지 않게 하려는 선택이기도 하다. 위저드 3단계의
  첫 메시지 미리보기도 인라인 div 대신 이 컴포넌트를 쓰게 바꿨다.
- **E2E는 진짜 PNG를 코드로 만들어 첨부한다**(`e2e/fixtures.ts`, 고정 시드 노이즈 1600×1200 ≈ 5.7MB).
  바이너리 픽스처를 저장소에 넣지 않으면서 "수 MB 원본 → 리사이즈 통과" 경로가 매 실행 검증된다.

### 남긴 한계

- **이미지 검수·신고 없음**(범위 제외). 올린 사람만 제한될 뿐 내용 심사는 없다.
- **커버 교체 불가** — 플롯 수정 화면 자체가 스코프 밖이다. 이미지 응답이 immutable 캐시라
  교체가 생기면 새 id를 발급하는 구조로 가면 된다.
- **연결되지 않은 이미지가 DB에 남는다.** 업로드 후 플롯을 안 만들면 고아 행이 된다.
  데모 규모에서는 무시하지만, 실서비스라면 만료 정리(TTL)가 필요하다.
- **저장은 DB(bytea)** — `ImageStore` 인터페이스 뒤에 있어 교체 지점은 분리돼 있지만,
  구현체 자체는 오브젝트 스토리지 + CDN이 아니다. 위 세 가지와 함께 README 재작성(09-02) 시
  "한계" 항목에 옮겨 적을 내용이다.
